# 总体设计

你的计算机配有*输入*与*输出*设备，它们分别负责从你那里接收信息、以及把信息显示给你。这些输入设备的形式例如：

- 键盘
- 鼠标
- 触摸板
- 触摸屏
- 数位板

你的输出设备通常表现为显示器，位于你的桌上、笔记本上或移动设备上。这些资源在你的所有应用程序之间共享，而 **Wayland 合成器**的职责就是把输入事件分派给恰当的 **Wayland 客户端**，并把它们的窗口显示在输出设备上恰当的位置。把你这所有的应用程序窗口汇集起来、一并显示到某个输出设备上的过程称为*合成（compositing）*——因此我们把执行这一工作的软件称为*合成器*。

## 实践之中

桌面生态系统中存在许多彼此独立的软件组件。有用于渲染的工具如 Mesa（以及它的各个驱动），有 Linux 的 KMS/DRM 子系统，有借助 GBM 进行的缓冲区分配，有用户态的 libdrm 库，有 libinput 与 evdev，还有更多更多。别担心——理解 Wayland 并不需要你精通其中大多数系统，而且无论如何，它们大体上超出了本书的范围。事实上，Wayland 协议相当保守而抽象，一个基于 Wayland 的桌面即便完全不牵涉这些软件，也能轻松地被构建起来，并运行大多数应用程序。话虽如此，对这些部件是什么、如何工作有一个表层的了解仍是有益的。让我们从最底层开始，一路向上。

## 硬件

一台典型的计算机配备了几件重要的硬件。在机箱之外，有你的显示器、键盘、鼠标，也许还有些音箱和一个可爱的 USB 暖杯垫。而在机箱*内部*，则有若干组件负责与这些设备对接。例如，你的键盘和鼠标大概插在 USB 端口上，而你的系统为此配有专门的 USB 控制器。你的显示器则插在 GPU 上。

这些系统各有自己的职责与状态。例如，你的 GPU 拥有以内存形式存在的状态，用来存放像素缓冲区；它还有诸如把这些缓冲区*扫描输出（scan out）*到你的显示器这样的任务。你的 GPU 还提供了一个处理器，它被专门调校得擅长高度并行的任务（比如为一台 1080p 显示器上的 2,073,600 个像素各自算出正确的颜色），而做别的一切都很糟糕。USB 控制器则承担着令人望而生畏的职责：实现那份出了名枯燥的 USB 规范，以便从你的键盘接收输入事件，或者指示你的杯垫加热到一个经过精心挑选的温度——既能避免吃官司，又能用冷掉的咖啡让你抓狂。

在这个层面上，你的硬件几乎不知道你的系统上正运行着什么应用程序。硬件提供一个接口，人们可以命令它执行工作，而它就照做——不管是谁下的命令。正因如此，只允许一个组件与它对话……

## 内核

这份责任落到了内核身上。内核是一头复杂的巨兽，所以我们只聚焦于与 Wayland 相关的那些部分。Linux 的职责是为你的硬件提供一层抽象，使其能够被*用户态*——也就是我们运行 Wayland 合成器的地方——安全地访问。对于图形而言，这被称为 **DRM**，即*直接渲染管理器（direct rendering manager）*，它高效地把来自用户态的工作交给 GPU 去执行。DRM 的一个重要子系统是 **KMS**，即*内核模式设置（kernel mode setting）*，用于枚举你的显示器并设置诸如所选分辨率（也就是它们的“模式”）之类的属性。输入设备则通过一个名为 **evdev** 的接口进行抽象。

大多数内核接口都通过 `/dev` 下的特殊文件暴露给用户态。就 DRM 而言，这些文件位于 `/dev/dri/` 下，通常以主节点（primary node，例如 `card0`）的形式存在，用于模式设置这类特权操作；以及以渲染节点（render node，例如 `renderD128`）的形式存在，用于渲染或视频解码这类非特权操作。就 evdev 而言，其“设备节点”是 `/dev/input/event*`。

## 用户态

现在，我们进入了用户态。在这里，应用程序与硬件相互隔离，必须经由内核提供的设备节点来工作。

### libdrm

大多数 Linux 接口都有一个用户态的对应物，它提供一套还算友好的 C API 来操作这些设备节点。libdrm 就是这样一个库，它是 DRM 子系统的用户态部分。Wayland 合成器使用 libdrm 来执行模式设置以及其他 DRM 操作，但 Wayland 客户端通常不会直接使用它。

### Mesa

Mesa 是 Linux 图形栈中最重要的部分之一。它提供的功能包括：面向 Linux 的、经过厂商优化的 OpenGL（以及 Vulkan）实现，以及 **GBM**（Generic 缓冲区 Management，通用缓冲区管理）库——一层位于 libdrm 之上、用于在 GPU 上分配缓冲区的抽象。大多数 Wayland 合成器都会经由 Mesa 同时使用 GBM 与 OpenGL，而大多数 Wayland 客户端至少会用到它的 OpenGL 或 Vulkan 实现。

### libinput

正如 libdrm 抽象了 DRM 子系统，libinput 提供了 evdev 的用户态一端。它负责从内核接收来自你各种输入设备的输入事件，把它们解码成可用的形式，并转交给 Wayland 合成器。Wayland 合成器需要特殊权限才能使用 evdev 文件，这就迫使 Wayland 客户端必须经由合成器来接收输入事件——例如，这可以防止键盘记录。

### (e)udev

处理内核中新设备的出现、为 `/dev` 中由此产生的设备节点配置权限、并把这类变更的消息发送给系统中运行的应用程序——这些是落在用户态头上的职责。大多数系统为此使用 udev（或其分支 eudev）。你的 Wayland 合成器使用 udev 来枚举输入设备与 GPU，并在有新设备出现或旧设备被拔出时收到通知。

### xkbcommon

XKB 是 X keyboard 的缩写，是 Xorg 服务器最初的键盘处理子系统。若干年前，它从 Xorg 代码树中被提取出来，成为一套独立的键盘处理库，如今它与 X 已没有任何实际关系。libinput（连同 Wayland 合成器）以扫描码（scancode）的形式传递键盘事件，而扫描码的确切含义因键盘而异。把这些扫描码转换为有意义且通用的按键“符号”，正是 xkbcommon 的职责——例如把 `65` 转换为 `XKB_KEY_Space`。它还包含一个状态机，知道在按住 shift 时按下“1”会输出“！”。

### pixman

一个简单的库，客户端与合成器都会用它来高效地操作像素缓冲区、对相交矩形做数学运算，以及执行其他类似的**像**素**操**控（pix**el** **man**ipulation）任务。

### libwayland

libwayland 是最常用的 Wayland 协议实现，以 C 语言编写，处理了大量底层的线上协议工作。它还提供了一个工具，可从 Wayland 协议定义（即 XML 文件）生成高层代码。我们将在第 1.3 节以及贯穿全书中详细讨论 libwayland。

### ……以及其他所有东西

到目前为止提到的每一个部件，在 Linux 桌面生态系统中都随处可见。除此之外，还有更多组件存在。许多图形应用程序完全不了解 Wayland，而是选择让 GTK+、Qt、SDL、GLFW 之类的库（以及许多其他库）去处理它。许多合成器选择用 wlroots 这类软件来抽象掉自己更多的职责，而另一些则把一切都自研实现。
