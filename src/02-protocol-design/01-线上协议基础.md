# 线上协议基础

**注意**：如果你只是打算使用 libwayland，本章是可选的——可以直接跳到第 2.2 节。

---

线上协议是一个 32 位值的流，以主机的字节序编码（例如 x86 系列 CPU 上的小端序）。这些值表示以下基本类型：

**int, uint**:32 位有符号或无符号整数。

**fixed**:24.8 位有符号定点数。

**object**:32 位对象 ID。

**new_id**:32 位对象 ID，在收到时为该对象分配 ID。

除了这些基本类型，还使用以下其他类型：

**string**：一个字符串，前置一个 32 位整数以指明其长度（以字节计），随后是字符串内容和一个 NUL 终止符，并以未定义数据填充至 32 位对齐。编码方式未加规定，但实践中使用 UTF-8。

**array**：一块任意数据的 blob，前置一个 32 位整数以指明其长度（以字节计），随后是数组的原样内容，并以未定义数据填充至 32 位对齐。

**fd**：在主传输上是一个 0 位值，但会借助 Unix 域套接字消息中的附属数据（msg_control）把文件描述符传递给另一端。

**enum**：取自一组已知常量枚举的单个值（或位图），编码成一个 32 位整数。

## 消息

线上协议是由这些基本类型构建而成的消息流。每条消息都是一个作用于*对象*的事件（在服务端发往客户端的消息的情形下）或请求（客户端发往服务端）。

消息头包含两个“字”（word）。第一个字是所作用对象的 ID。第二个字是两个 16 位值；高 16 位是消息的大小（包括消息头自身），低 16 位是事件或请求的操作码（opcode）。消息参数紧随其后，其依据是双方事先约定好的消息签名。接收方查找该对象 ID 的接口，以及由其操作码所定义的事件或请求，以此确定消息的签名与性质。

要理解一条消息，客户端与服务端首先必须建立起这些对象。对象 ID 1 被预分配为 Wayland display 单例，可用于引导（bootstrap）其他对象。我们会在第 4 章讨论这一点。下一章将介绍接口是什么，以及在假设你已经协商好一个对象 ID 的前提下，请求和事件如何工作。说到这个……

## 对象 ID

当一条消息带着 `new_id` 参数到来时，发送方会为它分配一个对象 ID——用于该对象的接口通过额外的参数来确立，或者针对该请求/事件事先约定好。这个对象 ID 可以用于后续消息，要么作为消息头的第一个字，要么作为 `object_id` 参数。客户端分配的 ID 范围是 `[1, 0xFEFFFFFF]`，服务端分配的 ID 范围是 `[0xFF000000, 0xFFFFFFFF]`。ID 从该边界下端开始，每次分配新对象时递增。

对象 ID 为 0 表示空对象（null object）；也就是不存在的对象，或显式地表示没有对象。

## 传输

迄今为止，所有已知的 Wayland 实现都工作在 Unix 域套接字之上。这么做有一个特别的原因：文件描述符消息。Unix 套接字是能够在进程之间传递文件描述符的最务实的传输方式，而这对于大数据量传输是必需的（键盘映射、像素缓冲区以及剪贴板内容是主要的用例）。理论上，也可以使用别的传输方式（例如 TCP），但总得有人想出另一种传递批量数据的办法。

为了找到要连接的 Unix 套接字，大多数实现就照 libwayland 的做法来：

1. 如果设置了 `WAYLAND_SOCKET`，就把它解释为一个文件描述符编号，连接在该描述符上已经建立，并假定父进程已经为我们配置好了连接。
2. 如果设置了 `WAYLAND_DISPLAY`，就与 `XDG_RUNTIME_DIR` 拼接，构成 Unix 套接字的路径。
3. 假定套接字名称为 `wayland-0`，并与 `XDG_RUNTIME_DIR` 拼接，构成 Unix 套接字的路径。
4. 放弃。
