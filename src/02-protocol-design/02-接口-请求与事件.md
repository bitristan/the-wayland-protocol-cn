# 接口、请求与事件

Wayland 协议通过发出作用于*对象*的*请求*和*事件*来运作。每个对象都有一个*接口*，它定义了可能有哪些请求和事件，以及各自的*签名*。我们来看一个示例接口：`wl_surface`。

## 请求

一个表面是一块可以被显示在屏幕上的像素盒子。它是我们用来构建诸如应用程序窗口之类东西的基本单元之一。它的其中一个*请求*——由客户端发往服务端——是 “damage”，客户端用它来表明表面的某部分已经改变、需要重绘。下面是一个在线上传输的 “damage” 消息的带注释示例（十六进制）：

```
0000000A    Object ID (10)
00180002    Message length (24) and request opcode (2)
00000000    X coordinate (int): 0
00000000    Y coordinate (int): 0
00000100    Width        (int): 256
00000100    Height       (int): 256
```

这是一段会话的片段——该表面早先已被分配，并被赋予 ID 10。当服务端收到这条消息时，它查找 ID 为 10 的对象，发现它是一个 `wl_surface` 实例。知道这一点后，它查找操作码为 2 的请求的签名。于是它就知道要预期四个整数作为参数，便可以对消息进行解码，并在内部派发处理。

## 事件

服务端也可以向客户端发回消息——事件。服务端可以针对 `wl_surface` 发送的其中一个事件是 “enter”，它在某个特定 output 上显示该表面时发送（例如，客户端可以据此调整它在 HiDPI 显示器上的缩放系数作为响应）。下面是这样一个消息的示例：

```
0000000A    Object ID (10)
000C0000    Message length (12) and event opcode (0)
00000005    Output (object ID): 5
```

这条消息通过 ID 引用了另一个对象：即该表面正在其上显示的那个 `wl_output` 对象。客户端收到它之后，会和刚才的服务端跳同一支舞。它查找对象 10，将其与 `wl_surface` 接口关联起来，并查找操作码 0 所对应事件的签名。它相应地解码消息的其余部分，同时也查找 ID 为 5 的 `wl_output`，然后在内部派发处理。
